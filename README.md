# DMP Ranking Tracker

公式ランキングと、取得できた大会成績から計算した追跡対象内の暫定ランキングを比較するアプリです。Node.js、Express、PostgreSQL、HTML/CSS/JavaScript を使用します。

## ローカル起動

Node.js 24、npm、専用の PostgreSQL データベースを用意します。設定やマイグレーションはこのアプリ専用のDBに適用してください。

```sh
npm ci
cp .env.example .env
npm run migrate
npm start
```

マイグレーション前に `.env` の `DATABASE_URL` を設定してください。管理画面を使う場合は `ADMIN_LOGIN` と12文字以上の `ADMIN_PASSWORD`、定期起動には十分に長いランダムな `CRON_SECRET` を設定します。初回起動時に管理者を作成します。同じログイン名で環境変数を変えても登録済みパスワードは変更されません。

- アプリは [http://localhost:3000](http://localhost:3000)、管理は [http://localhost:3000/admin](http://localhost:3000/admin) で開きます。ローカル管理画面は `NODE_ENV=production` を設定せずに起動します。
- 管理画面から対象期の開始日、終了日、新APIの期コード、旧サイトの期コードを入力します。初期ルールは CS 週上位2大会、CSE・GP・BN 別枠です。
- `ALLOW_DMP_FETCH=false` が既定です。外部データの取得許可と対象期の設定を確認した後に有効化します。管理の「公式更新確認」または認証付きcronで初期化を始めます。
- `RUN_WORKER=false` でWebからワーカーを分離できます。同じDBと環境変数を設定して `npm run worker` を実行します。常駐ワーカーは30秒間隔でキューを確認するため、DBをスリープさせたい運用ではWeb同居構成を使います。

## 自動テスト

```sh
npm ci
npx playwright install chromium
npm test
```

macOS ではインストール済みの Google Chrome があれば使用します。任意の Chromium 系ブラウザは `CHROME_PATH` で指定できます。HTTPとブラウザの統合テストは空きループバックポートを使用します。DBテストはその場で作る PGlite DB と匿名データを使い、DMP、Neon、Render には接続しません。

## データベース

| 用途 | テーブル |
|---|---|
| 選手と追跡 | `players`、`player_name_history`、`tracked_players` |
| 期と大会 | `seasons`、`aggregation_rules`、`events`、`event_results`、`event_result_changes` |
| 公式・週間・暫定 | `official_rankings`、`official_history`、`weekly_points`、`provisional_rankings`、`provisional_history`、`sync_discrepancies` |
| 運用と認証 | `fetch_jobs`、`fetch_logs`、`app_settings`、`admin_accounts`、`admin_sessions`、`backup_history` |
| 追加テーブル | `aggregation_batches` は変動の共通時点、`pending_personal_results` は未照合の個人成績、`job_event_pages` はページごとの一時保存、`schema_migrations` は適用済みSQL |

開催日の曜日はJST基準です。期は開始日・終了日を含み、大会を期で区切ってから月曜始まりの週へ割り当てます。同じ週にまたがる別の期のポイントは合算しません。同点の大会は開催年、店舗ID、大会ID、開催IDの順で安定して採用します。暫定同点は競技順位とし、表示順は公式順位、DMP IDの順です。

大会成績は大会IDとDMP IDの組に統合します。大会APIの内訳を優先し、個人成績の内訳が不明な場合はNULLを保存します。未照合の正のポイントは保留にし、暫定ランキングへの初期掲載を待機します。公式値による暫定値の上書きは行いません。過去時点で証拠不足の照合は比較不能として保存します。

## 内部API

| メソッド・ルート | 用途 |
|---|---|
| GET `/health` | HTTPプロセスの稼働確認 |
| GET `/api/version`、`/api/seasons`、`/api/state` | 変更検知、期、取得状況 |
| GET `/api/rankings` | `mode`、`season`、`q`、`limit`、`sort`、`dir`、`ids` で検索 |
| GET `/api/players/:id` | 選手の週間集計、大会成績、推移 |
| GET `/api/borders` | `n` は1〜200。公式スナップショットと暫定履歴から算出 |
| GET `/api/events`、`/api/events/:id` | `from`、`to`、`pref`、`grade`、`status`、`q`、`offset` による絞り込みと詳細 |
| POST `/api/watch` | `{ids, season}` でブラウザのウォッチ対象を更新。ブラウザ30人、期ごとにサーバー500人 |
| POST `/admin/api/login`、`/admin/api/logout` | 管理者セッション |
| GET `/admin/api/status`、POST `/admin/api/action` | 運用状態、追跡、個人・大会再取得、再集計、ルール、バックアップ、期確定 |
| POST `/internal/cron` | ヘッダー `X-Cron-Secret` で認証し永続キューに登録。HTTP 202 を返す |

ウォッチと管理のPOSTには `X-DMP-Request: 1` が必要です。公開ページに noindex を付けています。URLを知っている人は閲覧できます。

## 管理画面での初期検証

1. 管理画面で期を選び、「公式ランキングのみ取得」を押します。取得した公式順位を保存し、公式200位以内を追跡に登録します。この操作から個人成績や大会一覧の取得ジョブは作成されません。ジョブ完了後に「公式ランキングを開く」で同じ期を表示できます。
2. 「選手単位の集計検証」に登録済みの DMP ID または HN を入力して「この選手を検証」を押します。対象選手の個人成績と、未登録の大会キーの照合に必要な開催日・種別の一覧を取得します。期の集計ルールで計算し、管理画面に採用判定、週間ポイント、暫定合計、保存済みの公式ポイントとの差分、未照合大会、取得エラーを表示します。検証結果だけを保存し、通常の集計データや追跡状況への反映は行いません。
3. 補完を始めるときは「全体の初期化開始」を押します。保存済みの公式順位を使い、200位以内で補完が必要な選手の個人成績をキューに登録します。取得済み明細の再照合と不足大会一覧の取得まで進みます。

これらの操作には既存のワーカーと `ALLOW_DMP_FETCH=true` が必要です。取得を停止中の場合や、ワーカーがいない場合はキューで待機します。単独検証のアクセス範囲を確認する場合、既存ジョブが待機していない検証DBで操作してください。画面用の結果は管理者限定の `GET /admin/api/verification/:id?season=<期ID>` で取得されます。

### 初期化を途中から再開する

新しいコードの利用開始後、対象期の「不足大会を補完」を押すと、既存の未照合明細を使って再照合と大会一覧取得を起動します。「全体の初期化開始」は、未取得の公式上位選手が残っている場合に併用できます。外部スケジューラの接続は不要ですが、ワーカーが稼働し、一覧取得には `ALLOW_DMP_FETCH=true` が必要です。

不足大会は選手横断で集約し、期内の週・種別単位で共有します。種別が未確定の場合は対応する大会種別の一覧を照会します。一覧で解決した場合、補完処理から大会結果APIを登録しません。同じ週・種別でまだ見つからない大会は後続の実行に残し、正常終了した取得の再照会は最短24時間後です。公式値との照合で不一致が判明した場合は既存の再確認ルールが適用されます。

進捗は管理画面を開いている間に更新されます。人数は公式追跡対象、未照合とジョブの件数は対象期全体です。大会数は大会キーがある明細を重複排除した数です。本人確認エラーのログにはDMP ID、応答内の見出しと成績表の件数、照合用フィンガープリントを表示します。

### DB一括処理とジョブ計測への移行

稼働中の旧ワーカーが処理中のジョブを完了できる時間を確保し、ジョブが切れるタイミングで旧ワーカーを停止してから、新版を同じDBに接続します。ローカル環境で `npm run migrate` を実行するか、新版Webの起動時マイグレーションに任せます。`004.sql` はジョブ開始・終了時刻と工程別メトリクスの列、および実行中の工程用テーブルを追加します。旧データの時刻には推定値を入れません。旧版のエクスポートも新版に復元できます。

新版のワーカーを起動すると、既存キューの待機ジョブを引き継ぎます。異常終了で実行中のまま残ったジョブはリース満了後に再取得されます。未照合明細が残り、不足大会ジョブが待機していない場合に「不足大会を補完」を押します。既存DBと取得済み明細はそのまま利用できます。旧ワーカーと新版を同時に稼働させると、旧ワーカーには新しいリース更新と計測が適用されません。

管理画面は表示中に進捗とジョブ・ログを約5秒間隔で更新します。現在工程と、完了した試行の開始・終了・経過、工程別所要時間、通信量を表示します。開始・終了を記録していない旧ログは時刻欄が空欄になります。

テストデータによるローカル計測は `ALLOW_DMP_FETCH=false node scripts/benchmark-db.mjs` で実行できます。第1引数に旧版ディレクトリを指定すると同じデータで旧版も計測できます。計測はPGliteの一時DBとモック応答を使用し、DMPやNeonには接続しません。

### 本人照合エラーの選手だけを再試行する

取得リクエストには保存した元のHNを使います。照合と画面表示には数値文字参照を1回だけデコードした別の表記を使います。照合後に同名となる登録選手がいる場合は、対象選手が特定できるまで取得を失敗扱いにします。

新版を起動したら、管理画面で該当期を選び、ジョブ一覧で失敗した `personal` ジョブとDMP IDを照合します。「ジョブ再開」欄にはDMP IDではなく、再試行対象の既存ジョブIDを入力します。取得を一時停止した状態で対象だけを待機に戻し、他のジョブが実行対象に入っていないことを確認して「再開」を押します。完了済みの選手や大会を一括で再取得する操作は不要です。

### 暫定ランキングの公開と定期更新の状態

`005.sql` は公式上位200位以内（同順位を含む）の追跡状態と保存済み暫定順位から、期のデータ準備完了を補完します。準備済みの期は公式照合に差や判定不能があっても暫定順位を公開します。公式照合記録は管理画面に残ります。後から追加された選手は、集計が完了するまで暫定順位に入りません。

同じDBを使って新版に切り替える場合は、旧Webとワーカーを安全に停止して新コードを起動します。起動時に `005.sql` が適用されます。別に適用する場合は `npm run migrate` を使用できます。準備済みの成績や順位から判定するため、個人成績の再取得や再集計は不要です。

大会の登録検知、成績の取得元、公式反映の確認状況は別項目です。取得元や確認状況の件数は重複する場合があります。公式反映の自動確定は無効です。

「更新ルール上の次回時刻」は設定からの計算値です。「自動更新」は認証済みのcron受信とジョブ登録の記録に基づきます。履歴がなければ未確認、最後の正常な受信から2時間を過ぎれば異常として表示します。ジョブ登録が正常でも、ワーカーによる処理完了は別途ジョブ一覧で確認できます。

## バックアップ

定期と手動バックアップは `BACKUP_DIRECTORY` が指す永続ディレクトリに保存します。保存したファイルの SHA-256 を再読込で確認し、一時スキーマへ復元して内容を比較します。週次で直近4回を保持します。保存先未設定の場合は管理画面に `unconfigured` を記録します。本番で Render Free の一時ファイルシステムを永続バックアップ先に指定しないでください。

```sh
node --env-file=.env src/backup.js export ./backups/export.json
node --env-file=.env src/backup.js restore ./backups/export.json <SHA256>
```

エクスポート先ディレクトリは先に作成します。復元には別の空のDBを用意してマイグレーションを適用します。管理者とセッションはバックアップに含めず、復元先で管理者を作成し直します。期確定30日後の圧縮には、確定後の検証済みバックアップが必要です。

## 公開手順

1. データの取得・再公開許可、対象期の境界と期コードを確認します。利用許諾と再公開条件を確認できるまで、外部取得を無効のままにしてください。
2. ユーザーの指示後に、専用GitHubリポジトリを作成してコードを登録します。`.env`、実データ、バックアップは登録対象外です。
3. Neonで新しい Free プロジェクトと専用DBを作ります。接続文字列はダッシュボードからコピーし、TLSを有効にした状態で Render の秘密環境変数 `DATABASE_URL` に保存します。NeonとRenderは、選択可能な範囲で近いリージョンを用います。 [Neon 接続手順](https://neon.com/docs/connect/connect-from-any-app)
4. Renderで GitHub リポジトリに接続する **Web Service / Node / Free** を作成します。ビルドは `npm ci --omit=dev`、起動は `npm start`、ヘルスチェックは `/health` です。Nodeは `.node-version` を使用します。環境変数に `NODE_ENV=production`、`ADMIN_LOGIN`、`ADMIN_PASSWORD`、`CRON_SECRET`、`RUN_WORKER=true`、`ALLOW_DMP_FETCH=false` を設定します。初回起動時にマイグレーションされます。 [Render Free](https://render.com/docs/free)
5. HTTPSで管理画面にログインして期を作成し、空データの画面と認証を確認します。許可と対象期を確認してからDMP取得を有効化し、公式・個人の初期ロードと照合を管理画面で確認します。
6. cron-job.org から `POST https://<サービス名>.onrender.com/internal/cron` を送信し、ヘッダーに `X-Cron-Secret` を指定します。時刻は Asia/Tokyo で、00:00〜11:59は毎時0分、12:00〜15:59は0・30分、16:00〜23:59は10分間隔です。水曜日は12:00〜14:59に30分間隔、15:00〜17:59に5分間隔、18:00〜23:59に15分間隔の公式確認の枠を追加します。重複するスロットはDBで重複排除します。現在の設定と異なる頻度に変更する場合は外部スケジュールも合わせます。 [cron-job.org のタイムアウト](https://cron-job.org/en/faq/)
7. 冷間起動時と温間時の応答、次回起動時のリース再取得、実行件数、Render稼働時間、Neon CU時間と通信量を実測します。冷間起動が30秒を超える場合、長めのタイムアウトで認証付きPOSTを送るスケジューラも候補です。GitHub Actions の定期起動は最短5分で、遅延や欠落があり、実行枠も確認が必要です。 [GitHub Actions の定期実行](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)

2026年11月25日に確認した公開資料では、Render Free はワークスペース共有で月750時間、15分でアイドル停止、復帰は約1分です。Neonの公開料金表はプロジェクトあたり月100 CU時間、Postgres 1 GB、月5 GBの転送です。実契約はダッシュボードで確認してください。アプリのDB予算のデフォルトは500,000,000 Bです。 [Render Free](https://render.com/docs/free) [Neon 料金](https://neon.com/pricing)


### 取得方針と待機ジョブの移行

- 取得制限は管理画面の「概要」「更新管理」から確認できます。「システム設定」でDB容量予算、DMP受信本文予算、バックフィル日次上限、個人成績の再取得間隔を設定します。
- 受信本文は計測開始後のJST直近30暦日で集計します。従来のジョブログには送信本文も含まれ、クラウド事業者の課金対象通信量は各事業者の画面で確認します。通信予算の初期値は未設定です。
- DBと通信の比率のうち厳しい方で、70%から警告、80%からP4停止、90%からP3・P4停止、95%から手動を含む外部取得を停止します。
- P4はJSTの00:00〜12:00に、通常取得の空き時間で運転します。初期上限は1日50大会です。試行開始時にその日の大会枠を消費し、同日のリトライは同じ枠を使用します。日付をまたいで再試行すると新しい日の枠を使用します。

切り替え前に取得を停止し、実行中ジョブが0件になったことと復元可能なバックアップを確認します。旧スキーマのまま、接続先を確認したうえで次のコマンドを使うと待機ジョブの分類結果だけを確認できます。

```sh
node --env-file-if-exists=.env src/queue-preview.js
```

旧サーバーを停止してから、取得停止を維持した状態で `npm run migrate` を実行し、新版を起動します。006は旧ジョブを移行待ちとして識別し、新ワーカーはそれらのジョブをスキップします。管理画面の「ジョブ・ログ」でドライランを再確認し、承認後に「旧ジョブの分類を適用」を実行します。再分類・保留・取消件数と、通常の待機件数を確認した後に取得を再開します。元のジョブID、完了履歴、取得済み成績は保持されます。
